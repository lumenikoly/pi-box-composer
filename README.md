# pi-box-composer

Windows launcher на Rust + egui для Pi в **Podman** или **Docker Desktop**. Версия приложения — **0.0.5**. Старые настройки без выбора движка продолжают использовать Podman. Приложение основано на `Install-Pi.ps1` и `Start-Pi.ps1`; запускать эти скрипты отдельно не требуется.

## Быстрый запуск

Для готового `pi-box-composer.exe` Rust не нужен. Для сборки нужны Rust со стандартной Windows MSVC toolchain и Visual Studio Build Tools с компонентом **Desktop development with C++**.

```powershell
cargo run --locked
```

Сборка приложения:

```powershell
cargo build --release --locked
.\target\release\pi-box-composer.exe
```

## Релиз 0.0.5

В GitHub Actions вручную запустите **Release executable** из `main` с версией `0.0.5`. Workflow соберёт Windows x64, создаст тег `v0.0.5` и опубликует EXE с `SHA256SUMS`. Подробности — в [инструкции релиза](docs/RELEASE.md), изменения — в [CHANGELOG.md](CHANGELOG.md).

## Первая настройка

1. Установите [Podman Desktop](https://podman-desktop.io/docs/installation/windows-install) с rootless Machine **или** [Docker Desktop](https://docs.docker.com/desktop/setup/install/windows-install/) в режиме **Linux containers**. Соответствующая команда `podman` или `docker` должна быть доступна через PATH. После изменения PATH перезапустите launcher.
2. Нажмите **Настроить окружение**, выберите **Podman** или **Docker Desktop**, затем **Проверить и продолжить**. В **Установка и запуск** можно запустить установленный движок и посмотреть команды подготовки.
3. На экране **Сервер модели** укажите IPv4-адрес или DNS-имя llama.cpp, порт и API-токен, нажмите **Подключить**. Сервер должен быть доступен из контейнера прокси. `localhost` относится к самому контейнеру. Для Docker Desktop и модели на Windows-хосте используйте `host.docker.internal`; для другого компьютера — адрес в LAN. [Сеть Docker Desktop](https://docs.docker.com/desktop/features/networking/networking-how-tos/). Каталог окружения доступен в **Дополнительно**. Первый запуск скачивает образы и npm-пакеты.
4. Выберите модель и нажмите **Сохранить**. Контекст и лимит ответа доступны в **Лимиты модели**.
5. На экране **Проект** выберите рабочую папку и права доступа. По умолчанию выбран режим **Только чтение**.
6. Нажмите **Запустить Pi**. Launcher проверит проект и окружение, подготовит состояние и откроет отдельный PowerShell с интерактивным Pi. Терминал остаётся открытым после выхода для просмотра ошибки.

Сессии: **Новая**, **Продолжить** (`--continue`), **Выбрать прошлую** (`--resume`). Последний вариант открывает выбор сессии внутри Pi. Сохраняются последние десять успешно переданных терминалу проектов вместе с правами доступа; на главном экране показываются пять последних.

Главный экран содержит папку, права и выбор сессии. Настройка состоит из трёх экранов: движок → сервер → модель. Кнопка **Инструкция и команды** открывает отдельное окно с вкладками **Установка движка** и **Окружение Pi**, навигацией по шагам и карточками команд. У каждой команды есть пояснение, условия выполнения и кнопка **Копировать** с подтверждением **Скопировано**. В буфер попадает только выбранная команда; файлы конфигурации помечены путём и копируются отдельно. Команды доступны в этом окне, журнал — в меню **··· → Диагностика**. Используется системный Segoe UI: текст и кнопки 15 pt, заголовки экранов 26 pt. При отсутствии системного шрифта включается шрифт egui. Поля и кнопки используют общую сетку и высоту 44 px, поле папки — 48 px.

## Что делает мастер

| Шаг | Действие |
| --- | --- |
| 1 | Podman: проверка rootless. Docker: проверка Docker Desktop и Linux containers |
| 2 | Создание каталогов и запись `image/Containerfile`, `proxy/Caddyfile` |
| 3 | Сборка `localhost/pi-launcher-agent:1.3.0` |
| 4 | Создание и проверка внутренней сети Pi и внешней сети прокси |
| 5 | Передача токена прокси и запуск/пересоздание Caddy |
| 6 | Запрос `/v1/models` через прокси и проверка недоступности прямого соединения с llama.cpp |
| 7 | Запись модели, лимитов и политики разрешений |

Технические шаги находятся в **Инструкция и команды → Окружение Pi**. Кнопка **Выполнить шаг в launcher** запускает выбранный шаг; отдельные команды можно копировать для PowerShell. Условные действия отмечены отдельно, например создание Machine нужно только при пустом списке. При повторе шага последующие отметки сбрасываются. После перезапуска приложения проверки выполняются заново, а сохранённая конфигурация позволяет сразу перейти к запуску проекта. Выбор движка сохраняется; при переключении восстанавливается ранее завершённая конфигурация выбранного движка.

**Запустить Podman Machine** запускает существующую Machine. **Запустить Docker Desktop** выполняет `docker desktop start --timeout 60`. Если эта команда недоступна в установленной версии Docker Desktop, откройте приложение вручную и повторите проверку. Launcher использует активный Docker context и проверяет, что сервер сообщает Docker Desktop и Linux; сам context он не переключает.

Команды предварительного просмотра используют quoting PowerShell. Фоновые операции выполняются напрямую через `std::process::Command` с массивами аргументов. Запуск терминала использует литеральный массив аргументов в UTF-16 `EncodedCommand`; пути с пробелами, апострофами и `$` не превращаются в shell-код. Полный план содержит условные действия: существующие ресурсы сначала проверяются. Запись конфигурации выполняется Rust-кодом, а не shell-командами.

При отмене завершается текущий клиентский процесс выбранного движка. Уже созданные файлы и ресурсы остаются; операция сборки внутри VM может продолжаться. Повторный запуск шага проверяет имеющиеся ресурсы. Закрытие окна во время операции сначала запрашивает отмену.

Ответ списка моделей ограничен 1 МиБ, 4096 записями и 1024 байтами на идентификатор. Превышение любого предела выдаёт ошибку; список и идентификаторы не обрезаются. Обработка списка учитывает отмену и сохраняет порядок первого появления моделей. Вывод команд читается порциями; для машинной обработки усечённый вывод отклоняется, а длинный вывод сборки продолжает обрабатываться. Запись журнала ограничена 4 КиБ, очередь — 256 событиями, история — 1500 записями. При перегрузке пропускаются только записи журнала с итоговым уведомлением; результаты операций доставляются без пропусков.

## Данные и секреты

По умолчанию launcher сохраняет только настройки и список проектов в:

```text
%LOCALAPPDATA%\PiLauncher\launcher.json
%LOCALAPPDATA%\PiLauncher\environment\
  image\Containerfile
  proxy\Caddyfile
  config\models.json
  config\settings.json
  config\permissions.json
  config\ready.json
  state\projects\<SHA-256 пути>\agent\...
  docker\                     # независимое окружение Docker
    image\Containerfile
    proxy\Caddyfile
    config\...
    state\projects\...
```

Базовый каталог окружения можно изменить в UI. Podman сохраняет прежнюю структуру; Docker использует подпапку `docker`. Конфиги, история Pi и имена ресурсов разделены. Общими остаются список недавних проектов и права выбранной папки. Ресурсы имеют префикс `pi-ui-<хеш каталога>`, чтобы не пересекаться с оригинальными скриптами. Существующие контейнеры и сети с другим владельцем launcher не заменяет. Состояние оригинального `C:\Work\ai` автоматически не импортируется.

Токен не сохраняется в JSON launcher, исходниках, журнале или значениях аргументов процесса. Поле очищается после передачи фоновой операции.

- **Podman:** прежний механизм `podman secret create` через stdin. Пустое поле повторно использует секрет Podman. По умолчанию используется файловый драйвер; отдельного шифрования launcher не добавляет. [Секреты Podman](https://docs.podman.io/en/latest/markdown/podman-secret-create.1.html).
- **Docker Desktop:** обычная переменная `LLAMA_API_KEY` только в контейнере прокси. Значение передаётся через окружение дочернего процесса Docker CLI; команда содержит `--env LLAMA_API_KEY` без значения. Токен виден через `docker inspect` и не предназначен для хранения ценных внешних ключей. Пустое поле берёт токен из существующего прокси, причём вывод inspect не показывается и не попадает в журнал. Если прокси удалён, токен нужно ввести снова. Swarm, Docker secrets и отдельные volumes не используются.

Для смены токена введите новый и повторите шаг 5, затем проверки 6 и 7. Агент Pi реальный токен не получает ни в одном варианте.

## Границы доступа

- Проект монтируется в `/workspace` только для чтения или с записью. Docker использует `readonly` для первого варианта; запись — стандартный режим bind mount. В режиме чтения инструменты редактирования Pi выключены; `bash` остаётся доступен и может записывать в `/tmp` и `/state`.
- Состояние Pi всегда доступно на запись и отделено от проекта. В режиме `rw` изменения непосредственно затрагивают исходную папку Windows.
- Корневая файловая система агента read-only, capabilities сброшены, `no-new-privileges` включён, число процессов ограничено. Podman сохраняет rootless + `--userns=keep-id`. Docker запускает Pi от `1000:1000` в Linux VM Docker Desktop; это не rootless Podman. Домашняя папка Windows, SSH-ключи и сокеты движков не монтируются.
- В агент подключается только внутренняя сеть; прокси подключается к обеим сетям. Caddy разрешает только `/v1/models` и `/v1/chat/completions`; реальный API-токен передаёт прокси.
- Проверка прямого соединения требует код curl 7 или 28. Код 125 движка и другие ошибки не засчитываются как успешная изоляция. Proxy-переменные клиента Docker явно очищаются в контейнерах, чтобы не обходить внутреннюю сеть через пользовательские настройки CLI. Проверка относится только к указанному серверу; это не исчерпывающая проверка всех сетевых путей.
- Подключать корень диска, UNC-ресурс, каталог данных launcher, окружение или их родителей/потомков нельзя. Путь проекта разрешается через `canonicalize`; вложенные symlink/junction/reparse points отклоняются. Проверяется до 250 000 записей; для более крупных деревьев нужно выбрать более узкую папку. Проверка не защищает от изменения ссылок другим процессом после проверки.
- Политика расширения запрашивает подтверждения `edit`, `write`, `bash`, запрещает MCP и некоторые шаблоны команд. Это дополнительный слой, а не системная граница безопасности. `.env` и другие секреты внутри подключённого проекта физически доступны контейнеру, в том числе через `bash`. Используйте рабочую копию без секретов.
- LAN-соединение Caddy → llama.cpp сохранено как HTTP, как в исходном скрипте. HTTPS, скрытие файлов внутри проекта и отдельная копия/worktree не реализованы.

Образы Node/Caddy используют теги; npm-версии Pi и расширения закреплены на версиях исходного скрипта. Это не полностью воспроизводимая сборка контейнера по digest. При несовместимости этих версий сборка завершится видимой ошибкой.

## Разработка и проверка

```powershell
cargo fmt --check
cargo test --locked
cargo clippy --locked --all-targets -- -D warnings
```

Тесты проверяют оба движка: права монтирования и инструменты, flags сессий, отсутствие токена в аргументах агента, quoting терминала, проверку пути проекта, совместимость старых настроек, разделение профилей, Docker Linux/Windows preflight и обработку ошибок сетевой проверки. Три теста интерфейса проверяют мышь, активацию списка с клавиатуры и блокировку отключённой кнопки. Они не создают контейнеры и не обращаются к llama.cpp.

Изолированный запуск интерфейса с данными в отдельной папке:

```powershell
cargo run --locked -- --data-dir C:\Temp\PiLauncher-test
```

Параметр `--setup` открывает мастер настройки. `--smoke-test` закрывает окно через три секунды, не выполняя установку или запуск Pi. Полная проверка требует выбранного контейнерного движка, доступного llama.cpp и API-токена. Rust-приложение ориентировано на Windows; отдельный терминал других ОС в этой версии не реализован.


Для QA интерфейса доступна необязательная feature capture-ui: задайте путь PNG в PI_LAUNCHER_CAPTURE_TO и запустите cargo run --features capture-ui -- --instructions --smoke-test. Обычная release-сборка эту возможность не включает.
